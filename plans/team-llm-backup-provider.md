# Team LLM backup provider implementation plan

**Status: implemented and verified (22 October 2026).** The user authorized orchestration and delegation after settling the policy below. This plan records the authorized design and implementation evidence. Maintained operational documentation describes current behavior.

## Outcome and policy

Add one optional, administrator-configured backup provider and model per team, chosen from that team's ready providers and available models. The backup is a failure path, not an activation or eligibility path: every existing workflow gate, provider selection rule, role check, and validation contract still applies. The selection must be system-administrator controlled and must not expose credentials or grant transcript-content access.

All LLM workflows are in scope: ordinary note and Quick Action generation, follow-up/regeneration, hallucination checking, template suggestions, consultation-split analysis, split generation/recovery, and split verification. Each logical job may make at most one backup attempt. Provider failures (including timeouts, authentication/model errors) and provider-output validation failures may trigger it. Application quota exhaustion and provider hard-quota responses are terminal and must never trigger backup. Redaction failures, ownership/root/lifecycle/cancellation failures, missing or corrupt encrypted content, internal storage failures, and configuration authorization/snapshot mismatches must not be bypassed by fallback.

## Pre-implementation boundaries and constraints

- Provider attempts are database-backed quota records with unique `(correlation_id, attempt_number)` and durable submitted/settled/cancelled states (`app/models.py`, `app/services/quotas.py`). Runtime code commonly assumes attempt 1, so adding an attempt row alone is insufficient.
- Ordinary generated documents reserve attempt 1 with their outbox row, prepare redacted provider input, then commit the submitted boundary before invocation (`app/services/templates.py`). Generated document source and request payloads use owner encryption.
- Template suggestions reserve attempt 1 when queued and submit it in their worker (`app/services/template_suggestions.py`); the redacted request currently exists only in worker memory.
- Consultation-split generation has a business `ConsultationSplitExecution.attempt_no` used by partial-result recovery. That number represents recovery/re-generation lineage, not provider failover. Existing uniqueness and recovery assumptions must remain intact. Keep failover lineage distinct. Before implementation, choose and verify either multiple provider attempts per execution (requiring changes to the current one-attempt constraint and lookups) or a distinct linked fallback execution. Do not silently reuse partial-recovery numbering or weaken its guards.
- Split execution already persists owner-encrypted provider/request snapshots. Analysis and confirmed batch generation also persist logical-job provider snapshots. Extend those snapshot boundaries rather than inventing plaintext content storage.
- Existing request construction/redaction and strict structured-output validation are the source of truth. Reuse the same frozen redacted messages and output contract, rebuilding only the adapter-specific request envelope for backup; never rebuild a request from raw source after primary failure.
- Keep queue/outbox/task metadata, usage, audit, and quota rows free of prompts, provider responses, transcript content, and credentials.

## Required design and execution decisions

1. **Immutable queue-time choice.** At each logical-job queue boundary, snapshot the optional backup config identity, model, adapter/preset, safe base URL, and allowlisted provider settings alongside the primary choice. Store clinical-job snapshots using the existing owning user's encryption service and associated-data slots. Store only permitted non-secret IDs/model metadata in operational rows. A later admin edit must affect new jobs only.
2. **Provider availability and credential boundary.** Validate that the backup config belongs to the same team, is ready/selectable under existing provider rules, and that the chosen model is in its currently permitted model list at configuration time. At dispatch, revalidate the queued snapshot against the referenced config using existing snapshot validation. Resolve provider-specific credentials before the submitted boundary. A primary provider credential rejection or unavailable provider-specific credential may proceed to backup; the backup's credential failure cancels its reservation and terminalizes without charging it. Global Vault, user content-key, or encryption-service failures are internal infrastructure/storage failures and must not be bypassed. Do not snapshot or persist credentials.
3. **Per-source state, not a catch-all wrapper.** Introduce a small shared provider-attempt policy/execution helper for safe classification and common reservation/submission/settlement mechanics, with source-owned callbacks for row locks, snapshots, terminalization, and lifecycle. Do not wrap complete worker bodies in `except Exception` and retry on another provider. Each source must catch only provider invocation and output-validation failures; errors from redaction, ownership/root checks, cancellation, encrypted storage, or snapshot authorization remain terminal.
4. **Separate durable failover state.** Before dispatch, create the backup's distinct `ProviderAttempt` with a collision-free identity and explicit linkage to its primary attempt, owner/team/root linkage, model/adapter metadata, and its own token reservation. Add the minimum source/execution state needed to identify current provider attempt and transition (`primary` -> `backup` -> terminal) under existing lock order. Rework consumers that query attempt 1 to query the currently active attempt or all attempts as appropriate. Preserve a database-enforced unique key as the duplicate-delivery guard. Ordinary checker attempts already use later attempt numbers under the document correlation ID: do not assume number 2 is free. Split attempts currently require number 1 and a unique execution link; explicitly migrate and test any chosen change to that contract.
5. **Atomic transition and charging.** On an eligible primary provider/output failure, lock and revalidate the owning source and live transcript root; settle the primary using reported usage when available, otherwise conservatively as unknown; reserve backup quota based on the same frozen redacted request and the backup model/output cap; persist active-attempt state and commit before invoking backup. If quota reservation fails, atomically leave primary settled and mark the job terminal for quota exhaustion. No provider call occurs for an unsubmitted attempt.
6. **Quota classification, deadline, and timeout ambiguity.** Preserve a controlled, structured provider failure category through the bounded transport layer. In particular, `bounded_request` currently removes `temporary_capacity` from its final error (`app/services/llm_execution.py`), while Gemini can emit generic 429/`RESOURCE_EXHAUSTED` for hard quota as well as temporary capacity (`app/services/llm_adapters/gemini_enterprise.py`). Do not classify from provider message strings. Prove that exhausted known temporary-capacity retries can trigger backup while provider hard-quota responses remain terminal. Keep each attempt within its own bounded deadline. A primary timeout may invoke backup only after primary is durably settled unknown. A stale/expired submitted attempt discovered by another delivery or lifecycle reconciler must not be replayed or start backup from a duplicate worker. This may charge both providers when primary acceptance is uncertain, the explicit cost of timeout fallback.
7. **No loops and deterministic delivery.** The backup is always the final provider dispatch for that logical call. Re-delivery must follow source state and never create a second backup attempt or invoke an already-submitted attempt again. Preserve deterministic outbox IDs, claim/idempotency behavior, and existing late-result/root-expiry protections. A late primary result after transition to backup cannot overwrite backup output or terminal source state.
8. **Selection/config lifecycle.** When an admin clears or changes backup selection, queued jobs keep their frozen selection. Config deletion/revision must follow current live-reference blockers/detachment rules and must not invalidate an in-flight snapshot or remove the credential needed by a queued job before its reference is durably removed. Preserve the established Vault cleanup commit ordering.
9. **Output and workflow semantics.** Validate each provider response against the same existing contract before persistence/display. Invalid primary output may trigger the single backup; invalid backup output terminates the job. For checker/fail-open flows, preserve current explicit workflow gates and outcomes; backup availability does not turn a skipped or ineligible checker into an active one. Preserve split partial-result acceptance/recovery and distinguish its recovery lineage from provider failover.

## Acceptance criteria

- One optional team backup is selectable only by authorized system administrators from ready same-team providers/models, and existing workflow gates remain authoritative.
- Every newly queued logical job freezes both provider choices and reuses only owner-encrypted, redacted request/source snapshots.
- Each actual provider dispatch has its own durable, correctly bounded quota attempt; no pre-submit credential failure consumes quota; submitted unknown outcomes settle conservatively.
- A job can reach at most primary plus one backup, and every retry, duplicate delivery, outbox recovery, lifecycle cleanup, deletion, expiry, and late response follows durable state without repeat dispatch or stale result promotion.
- Provider/output failures can reach backup; quota exhaustion is terminal; privacy, ownership, redaction, storage-integrity, cancellation, and root-lifecycle failures fail closed without fallback.
- Split recovery lineage and partial-result behavior remain distinct from provider failover, and generated outputs remain drafts requiring clinician review.
- Focused tests, relevant route authorization audit, migration checks, and maintained-document validation pass; current operational docs describe implemented behavior accurately.
