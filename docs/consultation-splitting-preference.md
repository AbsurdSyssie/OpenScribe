# Consultation-splitting preference rollout

Status: current rollout-gate behavior. The API-only analysis queue/projection, owner review-draft routes, passive existing-draft review/edit modal, durable Generate-intent start and server-side progress, browser Generate interception, SSE-first restoration polling, and explicit **Continue as one note** consumption are implemented. Bundled one-call generation, optional bundled verification, provider submission, encrypted snapshot reads, quota/usage settlement, and partial recovery are implemented. Deployment-like rollout checks remain before enablement.

## Preference and deployment gate

When consultation splitting is available to the owning clinician, the note toolbar also shows **Multiple problems** beside **Create** or **Regenerate**. This consultation-specific mark is stored on the transcript root and is restored when the clinician returns to that consultation. Selecting it only records the request for a review; it does not start analysis or generation. While the mark is being saved, Create and dictation-led generation are unavailable. A failed save restores the prior mark.

On Create, the server snapshots whether the request needs manual split review. The marker can request review even if the automatic preference is off, but it cannot bypass availability, owner, retention, redaction, template, provider, or authorization checks. A marked consultation that produces zero or one detected problem enters editable review so the clinician can add a problem or choose **Continue as one note**. Unmarked `not_required` results continue as one note automatically. Changing the marker after Create does not change an accepted request. A reload restores the persisted mark, safe pending/failed intent state, and any existing server review state; it does not create a new request or open review automatically.

**Workspace → Preferences** can show **Split a consultation into separate notes** when the deployment sets `CONSULTATION_SPLITTING_ENABLED=true`. The setting is owner-scoped and defaults off. The database stores only an explicit `true`; a missing or legacy `false` value means off.

When the deployment gate is false, OpenScribe hides the control and treats the capability as off. The ordinary app-preferences API may still store the inert preference so whole-preference saves do not erase it before a later rollout.

The owner transcribe workspace exposes `consultation_splitting_available` in REST and SSE, and `consultationSplittingAvailable` in the initial browser bootstrap. It represents the deployment and eligible-owner boundary. `consultation_splitting_enabled` is the effective new-Create gate: it is true when availability holds and the owner has automatic splitting enabled or the active transcript is marked **Multiple problems**. It is false for missing users, system administrators, an unmarked consultation with the automatic preference off, or a disabled deployment gate. A leader's management role never grants access to another user's transcript-derived content. The deployment variable is never sent to the browser, and neither value is derived from browser state.

With availability and the owner's automatic preference enabled, an owner may call `POST /api/v1/transcripts/{transcript_id}/consultation-split-analysis`. It calls the existing source-bound queue/reuse service. New Create intents use the same automatic preference or the active transcript's persisted marker. Responses expose only an analysis ID, bounded status, safe error code, timestamps, manual-review state, and validated topic UUID/title/primary/disposition/template ID fields. Workspace REST and SSE use a read-only projection; they never run redaction, invoke a provider, persist state, or retry. The route remains owner-only, CSRF-protected, rate-limited by the existing LLM limits, and `no-store`.

When availability is off, new split actions return `403 consultation_split_disabled` and workspace split projections are absent. When availability remains on but both the automatic preference and marker are off, new automatic split work is unavailable. An exact owner intent already accepted by the server remains visible and actionable through its `analysis_pending` and `confirmed` states after a later preference opt-out; that opt-out cannot leave accepted work invisible. Availability, owner/team scope, retention, source freshness, and exact analysis/intent/batch binding still apply. **Retry missing notes** and **Keep available notes** require availability and reject before looking up a transcript or batch when it is absent; they create no quota, outbox, or document side effect. See [environment.md](environment.md#provider-rollout-controls) and [api.md](api.md#llm-configuration-selection-and-preferences).

## Durable Generate intent foundation

`consultation_split_intents` now persists the identity of one future owner **Generate** action. It has a UUID idempotency key unique to that owner, owner/team/transcript IDs, the transcript retention deadline, and one owner-encrypted JSON snapshot of the selected template/version and ordinary-generation configuration. It has no live template/version reference and stores no template name, prompt, configuration, source, or patient content in plaintext.

The API-only `POST /api/v1/transcripts/{transcript_id}/consultation-split-intents` starts that verified service. It accepts a strict JSON body with UUID `client_idempotency_key` and UUID `selected_template_id`; malformed UUIDs or unknown fields return `422` even when the key is already known. It then returns only nullable `intent_id`, nullable `intent_status` and safe `intent_error_code`, `idempotency_replayed`, the server-snapshotted `manual_review_requested` boolean, and a bounded existing analysis projection. It returns `202` for queued or processing analysis and `200` for terminal, incomplete, or stale results. For a syntactically valid same owner key, replay happens before a current gate or changed request payload is considered, so it returns the original operation rather than retargeting it. New keys remain gated in the service. The route is owner-only, CSRF/origin protected, no-store, and subject to both existing LLM generation rate limits.

The service validates availability, the effective new-Create gate, and selected template, then prepares the current redacted source and commits a new intent with any reusable analysis, encrypted execution snapshots, quota reservation, and deterministic outbox row in one transaction. It snapshots the server-derived manual-review decision at that point. It publishes only after commit. A replay of the same owner key returns the original intent and encrypted selected-at-submit snapshot without new work while its transcript and linked analysis remain available and in the same owner/team/transcript scope; otherwise it fails closed. Different owner keys may bind to the same current analysis and dispatch chain. A failed immediate publish leaves the durable outbox pending for its normal retry path.

The browser captures the target transcript and selected template when the owner selects **Create** or **Regenerate**. A shared Create barrier waits for target-bound Working note and dictation saves, then rechecks the active transcript before it submits this endpoint with a browser UUID key. Switching consultations cannot redirect those saves to the newly active consultation. Source saving and required redaction preparation remain synchronous before intent acceptance; a failure before the server accepts the request has no durable Create intent. After acceptance, the intent and its progress-dispatch outbox row are committed with the selected-at-submit snapshot and analysis binding. It never calls `/generate-output` on this path. Duplicate clicks share one in-flight browser operation; only an ambiguous network or 5xx result reuses its key. The nullable analysis link uses `SET NULL`, so independent analysis removal cannot erase the idempotency record or its encrypted selected-at-submit snapshot; transcript deletion remains the content deletion root.

Each accepted intent has its own deterministic `openscribe.process_consultation_split_intent` outbox dispatch. The worker waits with bounded exponential retry while analysis is queued or processing. When analysis becomes terminal, it either queues the saved ordinary one-note generation for an unmarked `not_required` result, or initializes/reuses the exact intent-bound draft for a ready result or a marked `not_required` result. A later preference opt-out does not revoke that accepted intent. The saved one-note continuation keeps its existing accepted-snapshot behavior; analysis, review, confirmation, and batch actions still enforce deployment availability, owner eligibility, transcript-root retention, analysis ancestry, and source freshness. Expired/deleted roots, stale sources, failed analysis, or unsafe state stop without generating content. A failed intent records only a safe `error_code` and `completed_at`. Pending and failed intent state contains only intent ID, analysis ID, status, manual-review flag, and safe error code. The exact accepted intent also remains available for its owner to review and confirm after preference opt-out, while deployment availability still controls access. Task payloads contain only the intent UUID. Unexpected exceptions are retried without exposing exception text. No new Beat schedule is needed; existing outbox publication and quota lifecycle handling recover dispatch.

## Passive one-note persistence foundation

An intent now also supports `bypassed`, which means its logical Generate action was consumed by one-note flow. It does not mean a provider call succeeded. A bypassed intent may link to one ordinary `GeneratedDocument`; the nullable unique link stores only that document ID, not note content. Deleting the document clears the link with `SET NULL` and leaves the intent bypassed, so it cannot become reusable. Transcript deletion still removes the intent and document.

The one-note consume operation validates the expected nested transcript plus shared owner/team/transcript/retention ancestry under canonical locks, compares current clinical sources with the saved encrypted analysis state, and ignores candidate-template metadata changes. It requires the live template parent to stay active and accessible, but uses the immutable submitted version, prompt, structured sections, and generation options. It creates the normal queued document, quota reservation, provider attempt, and outbox row atomically, then marks the intent bypassed and binds the document before best-effort publication. It does not resolve credentials or call a provider. The server progress worker calls this same operation for an unmarked `not_required` analysis; duplicate deliveries observe the consumed intent and do not create another document. A deleted child stays consumed.

`POST /api/v1/transcripts/{transcript_id}/consultation-split-intents/{intent_id}/continue-as-one-note` has no body and is protected by the normal full-context, CSRF/origin, no-store, and LLM-generation transport-limit controls. New consumption returns `202`; a bound-document replay returns `200`; and a deleted-child replay returns `200` with `document: null` and `consumed_document_deleted: true`. Its response has only the intent ID, replay flag, nullable generated-document detail, and deletion flag. It does not expose source, provider, quota, outbox, or snapshot data.

## Review draft API

With availability enabled, only the normal owning user may use `POST`, `GET`, `PUT`, or `POST .../consultation-split-draft/confirm`. Team leaders and system administrators cannot read or change a draft. The transcript retention root remains authoritative.

Confirm freezes redacted sources, manual-PII protections, the confirmed review plan, and exact selected template versions under the owner DEK. It requires an eligible selected LLM configuration and model. After it proves sources are fresh under the canonical source locks, it snapshots the current transcript draft with the existing empty-version path and binds that immutable version to the batch. This gives every split document a transcript-version lineage even when only a Working note or saved dictation supplied provider input. Those source-only analyses correctly retain null analysis `transcript_version_id` and `redaction_run_id`; the encrypted batch source snapshot remains provider truth. In the same transaction it creates one encrypted canonical provider request, write-once encrypted provider snapshot, generation execution, quota reservation, and deterministic outbox row; it creates no document and does not resolve credentials or invoke a provider. Generation rejects a missing or wrong-root batch binding and never creates a version in a worker. Failure to construct that queue rolls the whole confirmation tree back. Repeating the same intent returns the existing batch without reconsidering a later draft timestamp or reserving quota again. A one-note bypass and a confirmed split are mutually exclusive terminal intent states.

The provider receives only redacted split inputs. After validated output reaches the owner-only materialization boundary, the service restores placeholders from the batch's frozen encrypted PHI mapping before it stores each clinician-review document. Every materialization path (normal generation, **Keep available notes**, and verification finalization) requires the confirmation-bound transcript version; it never uses the nullable analysis source version. The accepted provider outcome remains encrypted in redacted form for recovery and audit; it is not rewritten during materialization.

Verification also checks that binding before submission and finalization. A missing or wrong-root version fails the batch with verification marked unchecked, cancels an unsubmitted attempt or settles a submitted attempt, and leaves accepted output and documents untouched. Verification cannot publish a draft with invalid lineage.

The service creates or reuses one draft for the exact accepted intent and its current `ready` analysis, or for a current `not_required` analysis only when the intent snapshot requested manual review. It accepts only the validated encrypted proposal and preserves proposal topic UUIDs. A global database constraint enforces one draft per analysis. The browser may explicitly initialize a review draft through `POST`; the server progress worker also does so after analysis completes. `GET` has no write path; when sources no longer match, it returns the existing draft as stale without changing its row. `PUT` replaces the whole ordered list and requires the exact `expected_updated_at`, so the server rejects a competing tab rather than merging it.

Titles are encrypted under the owner key. A replacement has zero to six distinct, nonblank topics, and exactly one primary topic when nonempty; the primary must be a separate note. Existing topic UUIDs must belong to the draft. New UUIDs come from the server and require an active, accessible template at its latest version. Existing proposed topics may have no template while the clinician edits. Responses include no source fingerprint, snapshots, provider state, or recoverable output.

## Passive existing-draft review modal

When workspace REST or SSE state already contains the current owner's review draft, the workspace shows **Review note split** under the existing split gates. An active draft can add up to six problems. Added problems begin as empty `separate_note` rows with a browser-only temporary key, then require a distinct title and current accessible template before Save. The modal omits that temporary key and `topic_uuid` from the `PUT`; the saved response replaces it with the server-assigned UUID. An unsaved added row can be removed. The modal edits active separate-note titles, primary choice, dispositions, and template choices, then saves the complete ordered draft through `PUT` with its exact `expected_updated_at`. Saving permits a valid one-note draft, but **Create** remains unavailable until the draft has two to six `separate_note` topics. When the exact pending intent is available in workspace state, the clinician may explicitly confirm or continue it; restoration alone never opens the modal, creates an intent, initializes a draft, saves source content, or confirms work. **Continue as one note** uses the template frozen when Create was pressed and does not apply later draft edits; Confirm freezes the edited review plan and its selected template versions. Drafts without an unambiguous current intent remain passive.

After **Confirm split**, the confirmed plan and queued batch remain immutable while generation is active. Once that batch reaches a terminal state, the workspace keeps the draft read-only until the clinician explicitly chooses **Review note split** or starts **Create/Regenerate**. That action saves current sources and starts a fresh review intent; normal edits and confirmation create a separate immutable batch and never alter the earlier batch. Merely receiving an SSE/poll update or reloading the workspace creates no intent and saves no source.

The modal keeps unsaved edits local while the draft remains the same. A competing save, stale source, unavailable draft, malformed proposal, or changed transcript fails closed; refresh can replace that state only when a successful workspace update supplies a current draft. The deployment and user gates remain default-off.

## Browser restoration polling

When the active transcript has an existing analysis in `queued` or `processing`, the browser refreshes the existing workspace GET while SSE is unavailable. SSE remains primary: an open EventSource pauses this fallback, and an error or unavailable EventSource resumes it. The browser uses bounded backoff (1.5, 3, 6, 12, then 15 seconds) and stops after 30 unchanged analysis states, a terminal or missing analysis, lost availability, page exit, or for the old transcript on a switch. After a switch, it may start again only if the newly active transcript has an eligible analysis. The server outbox task continues independently of whether the initiating browser stays open.

Polling uses the existing workspace request deduplication and applies only a response still matching the requested active transcript. While deployment availability holds, it restores only read-only workspace and split-review state for the owner's current automatic preference/marker or an exact accepted intent, including a pending or failed intent's safe metadata. Restoration without a matching local Create operation does not open the modal, create an intent, initialize a draft, show a new notification, invoke analysis or intent endpoints, or change ordinary **Generate**. A still-current local Create operation can also initialize/reuse its draft or consume its one-note intent through the existing POST routes; those actions are idempotent with the server progress task. Server continuation does not depend on that browser operation.

## Browser Generate completion

For a browser-started operation, queued and processing analysis use the existing accessible review status while the server progress task waits. After the intent is accepted, the browser refreshes the guarded workspace so the safe intent projection seeds later restoration. SSE remains primary and the existing bounded poller restores state when SSE is unavailable. The server creates or reuses the exact bound draft when analysis becomes ready, or is `not_required` for that intent's manual-review snapshot. The browser refreshes guarded workspace state and opens the matching review modal once for the still-current local Create operation. A draft restored without that local operation stays passive until the clinician explicitly opens it. A later preference opt-out does not hide or block that exact accepted intent; deployment availability and owner scope still apply.

`not_required` means analysis found fewer than two `separate_note` topics; `include_in_primary` and `exclude_from_notes` topics do not require a split review. For an unmarked accepted intent, the server progress task immediately consumes it through the dedicated one-note service and queues generation with the template frozen when Create was pressed; it does not ask for another click. For that intent's manual-review snapshot, the task initializes a draft and waits for explicit clinician review and confirmation or one-note continuation. `failed`, `stale`, and `incomplete` remain non-generating error states. The browser never calls `/generate-output` or sends template, configuration, source content, or patient content in the consume request. If the submitted template is no longer live, the intent fails safely and the clinician must choose a current template and start a new Create. A consumed intent whose child was deleted reports that it will not recreate the note.

Provider quota remains the business limiter. The intent-start route retains its existing transport limits. The database-only review-draft `POST` and `PUT` do not call an LLM and therefore have no dedicated LLM rate limiter.

After **Confirm split**, the Output note selector immediately shows one client-only placeholder pill per confirmed separate-note topic. The primary topic is selected first, and the existing note-generation loading screen reports queued, generating, or checking status. The placeholders create no database rows, cannot be edited or deleted, and do not add a second LLM call. SSE workspace snapshots replace each stable slot with the owner-projected generated document as it becomes ready; the existing bounded polling fallback is used only when SSE is unavailable. A terminal partial result keeps successful slots, marks failed slots unavailable, and leaves the existing Retry missing notes and Keep available notes actions in control. A full failure leaves the topic slots unavailable and re-enables **Create**. Regeneration keeps prior revisions in note history while replacing the current topic slots in place. Switching transcripts discards the browser-only slots.

## Partial recovery

A durably persisted provider response, including a malformed durable response, may retain valid topic outcomes encrypted, mark only failed requested topics, and queue one automatic retry using the initial execution's frozen provider configuration and model. A recovery response is parsed only against its failed-topic request set; retained validated siblings remain immutable context. A submitted attempt with no durable response, including a timeout or uncertain transport failure, never enters automatic recovery.

**Retry missing notes** is an explicit clinician action. It uses the current eligible provider selection, creates a fresh execution, quota reservation, and outbox row, and includes retained siblings only as immutable encrypted context. The batch lock lets a simultaneous automatic and manual retry create at most one second execution.

**Keep available notes** is an owner-only database action. It materializes each validated survivor once, replays the same children on a later request, and is rejected while a recovery execution is active. It never invokes a provider or consumes LLM quota. Workspace REST/SSE sends only safe status, counts, action flags, and IDs. It sends no topic output, provider, quota, or recovery detail. If the primary failed, the browser gives an accessible warning before Keep; after `completed_partial`, it states that a surviving secondary note was selected. Split children remain clinician-review drafts.

## Optional bundled verification

Before full materialization, and before **Keep available notes** for a partial survivor set, the service can use the independently configured team hallucination checker. A trusted partial initial response first reaches a terminal automatic-recovery decision. If recovery runs, verification waits for that recovery to complete or fail definitively; it then snapshots the stable complete set or stable survivors. The service never queues verification while a recovery is active. It queues one verification execution with its own reservation and outbox task. Credentials resolve outside the final transaction; the attempt commits as submitted before the one provider call. Duplicate delivery never makes a second call, and a recoverable encrypted response allows local finalization only.

Only an all-structured survivor set is eligible. The checker receives the immutable encrypted batch source, plan, clinical NLP snapshot, and exact survivor UUID set. It may return only the existing exact-substring structured-section edits. The service applies the complete valid envelope in memory and revalidates every corrected output before storing it in `verified_output_encrypted`; it never changes accepted output. Mixed/freeform sets have no patch protocol and are durably `unchecked`.

No selected/valid checker, unavailable credentials or quota, expiry, provider error or timeout, malformed response, or failed patch is fail-open. The batch records only bounded safe verification metadata and original validated outputs still materialize as clinician-review drafts. Workspace REST/SSE and browser status show only lifecycle state and correction count. They do not expose source material, verifier response, edits, provider metadata, or reasoning. Keep and retry controls stay unavailable while the batch is verifying.
