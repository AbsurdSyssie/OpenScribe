# Help page accessibility verification — 18 October 2026

This is a dated, focused automated assessment of the authenticated `/workspace/help` page and the shared navigation it uses. It is a test record, not a WCAG conformance claim. The audit used the isolated application fixture, a synthetic signed-in user, Playwright Chromium, and the locally pinned axe-core 4.10.3 bundle. It used no real patient data, provider calls, external asset requests, screenshots, or saved browser authentication state.

Command run:

```bash
APP_ENV=test COOKIE_SECURE_MODE=auto HSTS_SOURCE=app \
  .venv/bin/pytest -q --accessibility-audit tests/accessibility/test_help.py
```

The first focused run passed (**1 passed**). Axe scanned three authenticated states: desktop Help at 1280 × 800, narrow Help at 320 CSS pixels, and the open mobile drawer. It found zero violations. Desktop and narrow scans had no incomplete checks. Axe marked one mobile-drawer `color-contrast` check for manual review because it could not infer the background behind the sidebar identity label where it overlapped the drawer scrim. The test attempted a separate contrast measurement, but a later review found that the shared helper stopped at the first opaque ancestor; that original measurement was insufficient and is superseded by the correction below. That first axe run remains a point-in-time result. The local report path is ignored and overwritten by later runs: `test-results/accessibility/accessibility-audit-test_authenticated_help_accessibility_and_navigation.json`.

The test also checked the named Help article and topic navigation, all 13 section headings, the active Help sidebar link, visible skip-link and focus treatment, keyboard activation of a topic with focus moved to its heading, and the 24 CSS-pixel minimum for selected rendered Help/navigation targets. It exercised Help at 320, 375, and 740 CSS-pixel widths; selected sticky-sidebar and heading visibility while scrolling; 320-pixel text-spacing overrides; the desktop resize separator's keyboard controls and its separate click-to-resize buttons (no dragging); and simulated forced-colors focus visibility. The mobile drawer check covered Tab/Shift+Tab containment, Escape and close-button focus return, a pre-existing inert legal footer, inert page background while open, and exclusion of a recording-locked link from its keyboard cycle.

The audit uncovered and this change addressed visually unmarked Help links, horizontal overflow from the legal footer at narrow widths, missing skip and focus behavior for the Help topic list, background focus access while the mobile drawer was open, failure to restore a pre-existing inert state, the drawer's recording-locked link handling, and desktop resizing controls without keyboard or click alternatives. The desktop-only resize and collapse controls are hidden in the mobile drawer because they do not resize that drawer.

## Contrast-helper correction and final recheck

On review of the 11:36 UTC JSON report, the mobile drawer scan's nested `scans[].axe.incomplete` contained one `color-contrast` rule with two nodes (`.workspace-sidebar__identity > strong` and the email `<small>`). The earlier summary that read only the scan-level `incomplete` key was incorrect. Review also found `_contrast_ratios` stopped at the first opaque ancestor and therefore missed nearer nested opaque backgrounds. The helper now composites every ancestor background from outermost to innermost, and a browser regression verifies white text on a nested black background measures at least 20.9:1. The Help check waits for drawer animations to settle and computes both synthetic long-name and email ratios; it records 14.50:1 and 5.24:1 respectively. Axe still marks those two mobile nodes for manual review because the sidebar overlaps the scrim; the report retains that status rather than suppressing it.

The final sequential checks ran at 11:39 UTC. `APP_ENV=test COOKIE_SECURE_MODE=auto HSTS_SOURCE=app .venv/bin/pytest -q --accessibility-audit tests/accessibility/test_help.py` passed (**2 passed**). Then `tests/accessibility/test_pages.py::test_isolated_synthetic_pages_have_no_axe_wcag_violations` passed (**1 passed**) and `tests/accessibility/test_pages.py::test_narrow_reflow_and_keyboard_focus_are_visible` passed (**1 passed**), exercising the other consumers of the corrected shared helper. The latest Help report at 11:39 UTC has zero axe violations; desktop and narrow scans have zero incomplete checks, and the mobile drawer remains `needs_manual_review` for the two color-contrast nodes above. The route/render test was rerun at 11:40 UTC and passed (**32 passed**).

This evidence does **not** establish full WCAG 2.2 AA conformance. Actual 200%/400% browser zoom, screen-reader speech and workflows, native mobile assistive technology, real device/browser variation, and a full manual criterion review were not performed. Text spacing and forced colors were simulated in Chromium. Target-size checks cover selected Help and workspace navigation controls, not every target in the application.
