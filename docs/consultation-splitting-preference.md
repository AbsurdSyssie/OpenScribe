# Consultation-splitting preference rollout

Status: current rollout-gate behavior. The API-only analysis queue/projection, owner review-draft routes, passive existing-draft review/edit modal, effective capability gate shared by bootstrap, durable Generate-intent start, browser Generate interception, SSE-first restoration polling, and explicit **Continue as one note** consumption are implemented. Bundled one-call generation, optional bundled verification, provider submission, encrypted snapshot reads, quota/usage settlement, and partial recovery are implemented. Automated rollout evidence is complete; only deployment-like rollout checks remain before enablement.

## Preference and deployment gate

**Workspace → Preferences** can show **Split a consultation into separate notes** when the deployment sets `CONSULTATION_SPLITTING_ENABLED=true`. The setting is owner-scoped and defaults off. The database stores only an explicit `true`; a missing or legacy `false` value means off.

When the deployment gate is false, OpenScribe hides the control and treats the capability as off. The ordinary app-preferences API may still store the inert preference so whole-preference saves do not erase it before a later rollout.

The owner transcribe workspace exposes one server-derived `consultation_splitting_enabled` boolean in REST and SSE, and `consultationSplittingEnabled` in the initial browser bootstrap. It is true for an owning team user or team leader when both gates are true; it is false for missing users, system administrators, missing preferences, or a disabled deployment gate. A leader's management role never grants access to another user's transcript-derived content. The deployment variable is never sent to the browser, and this capability is not derived from browser state.

With both gates enabled, an owner may call `POST /api/v1/transcripts/{transcript_id}/consultation-split-analysis`. It calls the existing source-bound queue/reuse service. Responses expose only an analysis ID, bounded status, safe error code, timestamps, and validated topic UUID/title/primary/disposition/template ID fields. Workspace REST and SSE use a read-only projection; they never run redaction, invoke a provider, persist state, or retry. The route remains owner-only, CSRF-protected, rate-limited by the existing LLM limits, and `no-store`.

When either gate is off, new split actions return `403 consultation_split_disabled`, the capability boolean is `false`, and workspace analysis/draft projections are absent. This includes **Retry missing notes** and **Keep available notes**: they reject before looking up a transcript or batch and create no quota, outbox, or document side effect. Existing submitted work and lifecycle cleanup may still finish. The deployment gate remains false until the planned evaluation is reviewed. See [environment.md](environment.md#provider-rollout-controls) and [api.md](api.md#llm-configuration-selection-and-preferences).

## Durable Generate intent foundation

`consultation_split_intents` now persists the identity of one future owner **Generate** action. It has a UUID idempotency key unique to that owner, owner/team/transcript IDs, the transcript retention deadline, and one owner-encrypted JSON snapshot of the selected template/version and ordinary-generation configuration. It has no live template/version reference and stores no template name, prompt, configuration, source, or patient content in plaintext.

The API-only `POST /api/v1/transcripts/{transcript_id}/consultation-split-intents` starts that verified service. It accepts a strict JSON body with UUID `client_idempotency_key` and UUID `selected_template_id`; malformed UUIDs or unknown fields return `422` even when the key is already known. It then returns only nullable `intent_id`, `idempotency_replayed`, and a bounded existing analysis projection. It returns `202` for queued or processing analysis and `200` for terminal, incomplete, or stale results. For a syntactically valid same owner key, replay happens before a current gate or changed request payload is considered, so it returns the original operation rather than retargeting it. New keys remain gated in the service. The route is owner-only, CSRF/origin protected, no-store, and subject to both existing LLM generation rate limits.

The service validates the effective owner gate and selected template, prepares the current redacted source, then commits a new intent with any new reusable analysis, encrypted execution snapshots, quota reservation, and deterministic outbox row in one transaction. It publishes only after commit. A replay of the same owner key returns the original intent and encrypted selected-at-submit snapshot without new work while its transcript and linked analysis remain available and in the same owner/team/transcript scope; otherwise it fails closed. Different owner keys may bind to the same current analysis and dispatch chain. A failed immediate publish leaves the durable outbox pending for its normal retry path.

The browser captures the transcript and selected template when the owner selects **Create** or **Regenerate**, saves the Working note and dictation in that order, rechecks the active transcript, then starts this endpoint with a browser UUID key. It never calls `/generate-output` on this path. Duplicate clicks share one in-flight browser operation; only an ambiguous network or 5xx result reuses its key. After confirmation consumes that operation, the browser retires it, so a later Regenerate creates a new independent intent and immutable batch. The nullable analysis link uses `SET NULL`, so independent analysis removal cannot erase the idempotency record or its encrypted selected-at-submit snapshot; transcript deletion remains the only content deletion root.

## Passive one-note persistence foundation

An intent now also supports `bypassed`, which means its logical Generate action was consumed by one-note flow. It does not mean a provider call succeeded. A bypassed intent may link to one ordinary `GeneratedDocument`; the nullable unique link stores only that document ID, not note content. Deleting the document clears the link with `SET NULL` and leaves the intent bypassed, so it cannot become reusable. Transcript deletion still removes the intent and document.

The consume operation validates the expected nested transcript plus shared owner/team/transcript/retention ancestry under canonical locks, compares current clinical sources with the saved encrypted analysis state, and ignores candidate-template metadata changes. It requires the live template parent to stay active and accessible, but uses the immutable submitted version, prompt, structured sections, and generation options. It creates the normal queued document, quota reservation, provider attempt, and outbox row atomically, then marks the intent bypassed and binds the document before best-effort publication. It does not resolve credentials or call a provider. A deleted child stays consumed.

`POST /api/v1/transcripts/{transcript_id}/consultation-split-intents/{intent_id}/continue-as-one-note` has no body and is protected by the normal full-context, CSRF/origin, no-store, and LLM-generation transport-limit controls. New consumption returns `202`; a bound-document replay returns `200`; and a deleted-child replay returns `200` with `document: null` and `consumed_document_deleted: true`. Its response has only the intent ID, replay flag, nullable generated-document detail, and deletion flag. It does not expose source, provider, quota, outbox, or snapshot data.

## Review draft API

With both gates enabled, only the normal owning user may use `POST`, `GET`, `PUT`, or `POST .../consultation-split-draft/confirm`. Team leaders and system administrators cannot read or change a draft. The transcript retention root remains authoritative.

Confirm freezes redacted sources, manual-PII protections, the confirmed review plan, and exact selected template versions under the owner DEK. It requires an eligible selected LLM configuration and model. After it proves sources are fresh under the canonical source locks, it snapshots the current transcript draft with the existing empty-version path and binds that immutable version to the batch. This gives every split document a transcript-version lineage even when only a Working note or saved dictation supplied provider input. Those source-only analyses correctly retain null analysis `transcript_version_id` and `redaction_run_id`; the encrypted batch source snapshot remains provider truth. In the same transaction it creates one encrypted canonical provider request, write-once encrypted provider snapshot, generation execution, quota reservation, and deterministic outbox row; it creates no document and does not resolve credentials or invoke a provider. Generation rejects a missing or wrong-root batch binding and never creates a version in a worker. Failure to construct that queue rolls the whole confirmation tree back. Repeating the same intent returns the existing batch without reconsidering a later draft timestamp or reserving quota again. A one-note bypass and a confirmed split are mutually exclusive terminal intent states.

The provider receives only redacted split inputs. After validated output reaches the owner-only materialization boundary, the service restores placeholders from the batch's frozen encrypted PHI mapping before it stores each clinician-review document. The accepted provider outcome remains encrypted in redacted form for recovery and audit; it is not rewritten during materialization.

`POST` creates or reuses one draft for the current `ready` analysis. It accepts only the validated encrypted proposal and preserves proposal topic UUIDs. A global database constraint enforces one draft per analysis. `GET` has no write path; when sources no longer match, it returns the existing draft as stale without changing its row. `PUT` replaces the whole ordered list and requires the exact `expected_updated_at`, so the server rejects a competing tab rather than merging it.

Titles are encrypted under the owner key. A replacement has zero to six distinct, nonblank topics, and exactly one primary topic when nonempty; the primary must be a separate note. Existing topic UUIDs must belong to the draft. New UUIDs come from the server and require an active, accessible template at its latest version. Existing proposed topics may have no template while the clinician edits. Responses include no source fingerprint, snapshots, provider state, or recoverable output.

## Passive existing-draft review modal

When workspace REST or SSE state already contains the current owner's review draft, the workspace shows **Review note split**. The modal edits existing topic titles, primary choice, dispositions, and template choices, then saves the complete ordered draft through `PUT` with its exact `expected_updated_at`. A browser-started active review may explicitly choose **Continue as one note** using its durable intent. Passive restored drafts do not invent an intent or expose that action.

The modal keeps unsaved edits local while the draft remains the same. A competing save, stale source, unavailable draft, malformed proposal, or changed transcript fails closed; refresh can replace that state only when a successful workspace update supplies a current draft. The deployment and user gates remain default-off.

## Browser restoration polling

When the server-derived capability is enabled and the active transcript has an existing analysis in `queued` or `processing`, the browser refreshes the existing workspace GET while SSE is unavailable. SSE remains primary: an open EventSource pauses this fallback, and an error or unavailable EventSource resumes it. The browser uses bounded backoff (1.5, 3, 6, 12, then 15 seconds) and stops after 30 unchanged analysis states, a terminal or missing analysis, a disabled capability, page exit, or for the old transcript on a switch. After a switch, it may start again only if the newly active transcript has an eligible analysis.

Polling uses the existing workspace request deduplication and applies only a response still matching the requested active transcript. It only restores read-only workspace and split-review state. It does not open the modal, create or initialise a draft, show a new notification, invoke analysis or intent endpoints, or change ordinary **Generate**.

## Browser Generate completion

For a browser-started operation, queued and processing analysis show persistent accessible status beside **Create**. SSE remains primary and the existing bounded poller restores state when SSE is unavailable. When the matching analysis becomes ready, the browser creates or reuses its review draft through the existing draft `POST`, single-flighted by transcript and analysis, refreshes the guarded workspace, and opens the matching review modal once. Drafts restored from workspace remain passive.

`not_required` means analysis found fewer than two topics. For that browser-started durable intent, the browser immediately calls the dedicated `continue-as-one-note` route and generates with the template frozen when Generate was pressed; it does not ask for a second click. `failed`, `stale`, and `incomplete` remain non-generating error states and may expose the explicit recovery action only for that browser-owned intent. The browser never calls `/generate-output` or sends template, configuration, source content, or patient content in the consume request. If the submitted template is no longer live, the intent stays unconsumed and the clinician must choose a current template and start a new Generate. A consumed intent whose child was deleted reports that it will not recreate the note.

Provider quota remains the business limiter. The intent-start route retains its existing transport limits. The database-only review-draft `POST` and `PUT` do not call an LLM and therefore have no dedicated LLM rate limiter.

## Partial recovery

A durably persisted provider response, including a malformed durable response, may retain valid topic outcomes encrypted, mark only failed requested topics, and queue one automatic retry using the initial execution's frozen provider configuration and model. A recovery response is parsed only against its failed-topic request set; retained validated siblings remain immutable context. A submitted attempt with no durable response, including a timeout or uncertain transport failure, never enters automatic recovery.

**Retry missing notes** is an explicit clinician action. It uses the current eligible provider selection, creates a fresh execution, quota reservation, and outbox row, and includes retained siblings only as immutable encrypted context. The batch lock lets a simultaneous automatic and manual retry create at most one second execution.

**Keep available notes** is an owner-only database action. It materializes each validated survivor once, replays the same children on a later request, and is rejected while a recovery execution is active. It never invokes a provider or consumes LLM quota. Workspace REST/SSE sends only safe status, counts, action flags, and IDs. It sends no topic output, provider, quota, or recovery detail. If the primary failed, the browser gives an accessible warning before Keep; after `completed_partial`, it states that a surviving secondary note was selected. Split children remain clinician-review drafts.

## Optional bundled verification

Before full materialization, and before **Keep available notes** for a partial survivor set, the service can use the independently configured team hallucination checker. A trusted partial initial response first reaches a terminal automatic-recovery decision. If recovery runs, verification waits for that recovery to complete or fail definitively; it then snapshots the stable complete set or stable survivors. The service never queues verification while a recovery is active. It queues one verification execution with its own reservation and outbox task. Credentials resolve outside the final transaction; the attempt commits as submitted before the one provider call. Duplicate delivery never makes a second call, and a recoverable encrypted response allows local finalization only.

Only an all-structured survivor set is eligible. The checker receives the immutable encrypted batch source, plan, clinical NLP snapshot, and exact survivor UUID set. It may return only the existing exact-substring structured-section edits. The service applies the complete valid envelope in memory and revalidates every corrected output before storing it in `verified_output_encrypted`; it never changes accepted output. Mixed/freeform sets have no patch protocol and are durably `unchecked`.

No selected/valid checker, unavailable credentials or quota, expiry, provider error or timeout, malformed response, or failed patch is fail-open. The batch records only bounded safe verification metadata and original validated outputs still materialize as clinician-review drafts. Workspace REST/SSE and browser status show only lifecycle state and correction count. They do not expose source material, verifier response, edits, provider metadata, or reasoning. Keep and retry controls stay unavailable while the batch is verifying.
