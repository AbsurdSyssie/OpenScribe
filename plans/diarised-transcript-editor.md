# Implementation plan: structured diarised transcript editor

**Status: implemented on 22 October 2026; verification recorded below.** This plan captures the product decisions agreed with the user, including inline editing with shared autosave and editing only after transcription completes. It describes intended work; maintained operational documentation and executable code remain the sources for implemented behavior. The scope is an editable transcript experience for consultations whose STT results include speaker attribution, rather than a general redesign of the workspace or dictation.

## Outcome and agreed product behavior

For a consultation captured with diarisation enabled, show editable, ordered transcript blocks. A block displays `Speaker 1`, `Speaker 2`, etc.; an unattributed block displays `?`. Labels are presentation, not literal transcript text. Each speaker turn is an isolated edit unit: editing, selecting, pasting, or pressing Enter affects only that turn. An explicit action deletes a whole turn; deleting its last character does not implicitly delete the block. Text added outside a turn is a new unattributed block. Edits retain the original audio interval and show an edited marker; the interval must not be presented as word-accurate timing after text changes.

Persist turns as structured transcript-derived content encrypted for the owning user. Keep recording/session boundaries and scope speaker identities to a provider session/connection continuity boundary: equal numeric speaker IDs across independent scopes do not mean the same voice. A resumed recording/session or actual provider reconnect gets a distinct visible recording/section heading, with a clear indication that speakers are not matched across it. Current Deepgram streaming reuses its provider connection during ordinary checkpoints, pause, and resume, but can exceptionally rotate after an unconfirmed drain; preserve that distinction. Each uploaded audio file has its own speaker scope.

Use diarisation only for consultation capture where the administrator has enabled it for the team, provider configuration, and connection type, and the user has opted in. User preference is persistent across STT switches, defaults off, and is frozen for a capture. When the saved preference is on but the selected combination cannot diarise, preserve the preference and show a toast; availability returns automatically with an eligible selection. Show the limitation beside the preference. Show the stop/session-boundary warning once per user, and a missing-attribution toast at most once per recording/upload. Dictation is always excluded. Custom-provider live chunking is unavailable for diarisation in v1; do not imply cross-chunk identity continuity. Deepgram live and supported batch paths may be eligible. Missing speaker metadata keeps the transcription and uses `?`, with no invented labels or automatic provider retry.

The generated source should include structured turns and recording boundaries rendered into an unambiguous text representation for the model, plus a supplementary instruction that automated labels may be wrong and roles should be inferred cautiously from context. PII handling must first be tested with synthetic speaker-labelled examples; do not bypass redaction or presume that labels cause over-detection. Existing generated output remains a clinician-reviewed draft. No role reassignment UI is in v1.

## Pre-implementation baseline (22 October 2026)

- `app/templates/transcribe/_workspace.html` renders the current draft at `[data-active-draft]` as a read-only `div`, populated with `active_transcript.current_draft_text`.
- `Transcript` in `app/models.py` has one `current_draft_text_encrypted` field. `TranscriptVersion` stores encrypted flat text with monotonically assigned `version_no`; no turn/session schema exists.
- `TranscriptDetail` exposes `current_draft_text`; `TranscriptCommit` takes `text_encrypted`. `POST /api/v1/transcripts/{id}/commit` in `app/routes/api_routes.py` passes the submitted `text_encrypted` field as plaintext to the service boundary, which stores an encrypted flat text version. There is no optimistic version guard on this commit request.
- `app/services/transcripts.py` provides owner-key encryption helpers for current draft and transcript versions. `commit_transcript_text` creates a version, replaces the current draft, marks the transcript ready, then invokes preview redaction. Existing owner authorization, transcript expiry, source-writer locking, and transaction behavior must remain in force.
- The PII UI in `app/static/js/transcribe/app.js` maps codepoint offsets into the flat draft string and re-renders the whole draft markup. Those offsets cannot be reused over DOM text containing visual speaker labels/headings. Existing PII dismissal/redaction state is bound to transcript versions; changing text requires the normal new-version/redaction path.
- Generation and redaction use transcript versions and redacted snapshots. For example, `app/services/templates.py` resolves a transcript version and redaction before composing provider input; generated document source snapshots are retained for regeneration. Structured turns must be frozen alongside the exact flat canonical text/version used for redaction and generation, rather than reread later from mutable current turns.
- `app/routes/deepgram_live.py` keeps the Deepgram socket open for ordinary checkpoints and pause/resume, uses finalization/checkpoint confirmation, and may close/reopen after exceptional unconfirmed drain recovery. `docs/live_stt.md` documents this. Other live capture uses VAD chunk uploads. Deepgram and custom STT extraction live in `app/services/stt.py`, with the Deepgram streaming parser in `app/services/deepgram_streaming.py`.
- Team provider selection is split by purpose in `team_stt_selections`; provider configuration lifecycle and admin routes/templates are in the existing STT services and `app/routes/web_admin.py`. Personal preferences use existing user settings patterns. These are likely homes for controls, but the specific durable model and admin authority must be confirmed during implementation design.
- Current generation source also includes separate Working note and post-consultation dictation. Do not merge either source into the structured transcript model.

These findings describe current source, not the proposed behavior above. Maintained operational references include `docs/transcript-capture.md`, `docs/live_stt.md`, `docs/workspace.md`, and `docs/stt-config.md` (indexed by `docs/README.md`).

## Proposed data and lifecycle contract

Use an owner-encrypted structured snapshot on each immutable transcript version as the source of truth. Proposed `TranscriptVersion` extension: add a schema version and owner-encrypted JSON snapshot slot for diarised versions; serialize the ordered turns (stable turn UUID, session scope UUID, optional speaker key, start/end offsets, text, edited flag) using established owner-key JSON encryption. Keep clinical text and turn/session metadata encrypted together unless an executable query need proves some metadata may be plaintext. Existing `TranscriptVersion.text_encrypted` remains the deterministic canonical text projection and exact source text for current whole-transcript redaction. Migrate legacy versions with an explicit legacy schema version; readers must tolerate older flat-only versions. Add a root current-revision pointer only if necessary to bind the workspace view and mutation lock. If encrypted JSON snapshots have demonstrated size/performance problems, stop and present a dedicated-table alternative before implementation.

Every generated operation must capture ordered turns, scope headings, timestamps, edited state, and canonical projection in its existing owner-encrypted source snapshot. Retries and regeneration use that frozen snapshot. Do not put clinical text or serialized turns into a plain JSON column, audit metadata, queue metadata, or logs.

Retain a canonical flat-text projection that excludes speaker labels, recording headings, timestamps, and editor chrome. This projection is required to preserve current transcript-version/redaction services and codepoint offset semantics. Define projection once and deterministically, including Unicode normalization, line separators, leading/trailing whitespace, ordering, and empty deleted turns; never independently `.strip()` projection and version text because version snapshot matching relies on exact text. Persist the projection atomically with the corresponding structured edit/version. The visible label is joined to the projection by stable turn ID and a calculated codepoint range; do not derive PII positions from DOM `textContent`. PII highlights may be rendered per editable text node using an explicit projection-offset-to-turn-local-offset map. Stale PII highlights and dismissals must be invalidated by normal version identity when any turn changes; never apply offsets from an old version to new text. Existing copy-redacted-transcript behavior should operate on the canonical text and existing redaction service, not scrape the label-containing editor DOM.

Generation needs a span-aware mapping from exact canonical source offsets to redacted output offsets before speaker boundaries can be rendered for the model. Never slice redacted text using original offsets, since replacements change lengths, and never append raw turns after redaction. Preserve existing whole-transcript placeholder and dismissal behavior. Define and test a deterministic policy for PII spans crossing turn boundaries; if safe mapping cannot be guaranteed, fail closed and defer diarised generation. Bind redaction to both text version and structured snapshot identity, even when two revisions flatten to identical text.

The transcript root remains the retention/deletion root for all turns, turn snapshots, versions, and redaction associations. Preserve owner-only content access; team administration and provider-management metadata access must not expose turn text. Use database constraints for unique turn identity/order where appropriate, and validate all referenced turns and session scopes against the requested owning transcript. Apply deletion through existing root cascades and established cleanup paths.

## Editing and concurrency behavior

The current Working note autosave in `app/static/js/transcribe/app.js` debounces edits by 700 ms (`scheduleNoteAutosave`), records an edit version and optimistic `expected_updated_at` baseline, serializes writes (`noteSaveInFlight`), and queues a follow-up save when edits arrive during a request. A response clears dirty state only when its captured edit version is still current; otherwise it updates the baseline for the next queued save. `persistNoteEditsUntilDrained` flushes until clean. `persistPendingEditorsBeforeWorkspaceSwitch` gates workspace changes, and `saveWorkingNoteBeforeGeneration` flushes before generation. `noteSaveState.js` contains baseline selection helpers.

Reuse this code through a shared autosave controller extracted from the existing implementation, rather than copying its timers, queues, and dirty-state logic into a second editor. Use the controller for both the existing Working note/generated-note save path and the new transcript-turn editor, preserving existing note behavior. Share debounce scheduling, in-flight serialization, queued follow-up saves, edit-generation tracking, flush-until-clean, and disposal. Keep state isolated per editor/source and pass adapters for request building, revision-token handling, accepted-result updates, and status/conflict presentation. Transcript mutations still serialize across turns because they share a transcript revision. Keep the extraction focused on these common mechanics; do not combine source models, endpoints, or unrelated editor features.

Use direct inline editing with autosave, following the established Working note pattern. The text body of one turn is the editable boundary; speaker label, session heading, timing, and edited marker stay outside the editable node. Typing, paste, selection, deletion, and Enter remain inside that turn. Adding a block outside any turn creates an unattributed turn with no audio interval. Emptying a turn does not delete it. Whole-turn deletion remains an explicit, unobtrusive contextual action (for example, a menu on that turn), because accidental removal of its attribution and timing should require intent; it does not need a persistent toolbar. A deletion creates a new effective source revision and leaves prior immutable versions and queued generation snapshots unchanged for their existing lifecycle; do not create a separate permanent deleted-turn archive.

Agreed first-version write boundary: only permit edits when ingestion has completed and the transcript is in a stable ready state. During recording, queued transcription, finalization, unresolved recovery, or active provider writes, render turns read-only and explain why; do not race user edits with chunk application. Editing during active recording is outside this plan.

Add an `expected_version` or equivalent revision token to structured mutation requests and enforce it under the same source-writer lock used by transcript edits/split-source writers. It must identify both text and structured snapshot revision; matching plaintext alone is insufficient. On stale update, return a conflict with current safe revision metadata; never silently overwrite. For asynchronous workspace polling/hydration, if a local turn is dirty or saving, retain it and show a stale-version/reload conflict affordance instead of replacing the editor. On save success, replace local revision only after the server confirms and only if the response corresponds to the latest local edit version; on network failure retain the latest draft in page memory, show a save-failed state with retry, and do not write transcript content to localStorage, IndexedDB, URL, logs, or telemetry. On consultation switch/unload with a dirty edit, use a standard unsaved-change warning. Before generation, workspace navigation, or starting/restarting capture, flush edits until no save is queued or in flight; if flush fails or conflicts, stop the dependent action and preserve the draft in memory. Keep draft data only in in-memory component state.

## Implementation phases and likely touchpoints

### 0. Confirm contracts and inventory callers

Before coding, enumerate all readers/writers of flat transcript drafts and versions, including live streaming append, ingestion application, manual commit, PII highlighting/dismissal, redacted copy, template suggestions, consultation splitting, generation/quick actions, and tests. Confirm encryption APIs and transaction/lock boundaries. Validate the proposed encrypted version snapshot against existing payload bounds and bind the workspace to an explicit current structured revision. Confirm the currently implemented user preference and team STT admin configuration patterns from their executable sources. This plan is not authority to change those contracts.

Likely inspection points: `app/models.py`, `app/services/transcripts.py`, `app/services/transcript_streaming.py`, `app/routes/api_routes.py`, `app/schemas/transcripts.py`, `app/services/redaction.py`, `app/services/templates.py`, `app/services/consultation_split_sources.py`, `app/static/js/transcribe/app.js`, `app/templates/transcribe/_workspace.html`, and the associated tests.

### 1. Structured ingest and encrypted persistence

Add strict internal and API schemas for a turn and a bounded transcript revision. Normalize provider output at the established STT boundary into text, optional speaker key, time interval, and stream/session scope. Make provider speaker IDs opaque within the session; allocate durable session identity server-side. Deepgram live must preserve word speaker metadata across result messages and ordinary checkpoints on the same socket. Exceptional socket rotation opens a new scope. Supported Deepgram batch output maps into the same representation. Custom provider batch can map turns only when explicit configured mappings return valid speaker metadata. Custom provider live chunking is ineligible. Missing/invalid attribution leaves text intact with null speaker key.

Extend ingestion job/result persistence so an accepted result appends turns idempotently in the same durable application transaction as its job status and transcript revision. Replays of a committed ingestion must not duplicate turns. Ordering must follow existing job/chunk sequence and provider offsets, not arrival race order. Session/scope IDs are generated and checked server-side. Preserve exact audio/sample accounting and Deepgram connection/checkpoint semantics. Existing flat-only results keep their current behavior.

### 2. Version, projection, redaction, and generation bridge

Create one service boundary that reads/validates ordered turns for the owner, projects canonical text, creates an immutable transcript revision, and commits the projection plus structured snapshot transactionally. Route all turn edits and ingestion appends through this boundary. Keep flat text commits available for non-diarised transcripts; reject attempts to flatten/overwrite a transcript that owns structured turns unless a deliberately designed conversion path exists. Do not allow old clients to erase attribution by sending the legacy `TranscriptCommit` shape.

Bind each `TranscriptVersion` to the structured snapshot revision (or an explicit immutable turn snapshot) and its exact projected text. Run the established redaction flow against this projection first. Test speaker labels and metadata separately: labels are visible presentation but not automatically included in canonical text; generation rendering may include labels after the redaction service has protected turn text. Any included speaker markers must be fixed system-generated tokens and should be tested for detector behavior; no special redaction suppression or allow-list without evidence and explicit review. Fail closed if the redaction contract cannot be bound to the exact structured revision.

Update every generation entry point to freeze turns/session boundaries and render that immutable snapshot for the model, including ordinary generation, follow-up/quick actions, consultation splitting/regeneration, and template suggestions that read transcript content. Add typed snapshot schema/version compatibility so old generated documents and flat-only versions continue to load. Supplement the prompt only when that saved snapshot contains speaker labels. Instruction should convey that labels are automated and imperfect, infer clinical roles from context, do not assume exactly two speakers, and preserve uncertainty where evidence is unclear. Keep Working note and dictation as separate source slots. Preserve generated-document source snapshots for regeneration and ensure transcript edits after submission cannot alter an in-flight or historical generation.

### 3. Owner-only editor and safe edit operations

Extract and verify the shared autosave controller before wiring the turn editor. Add behavioral tests for its debounce, queued writes, stale responses, conflicts, failed-save retention, flush, and disposal, then run existing Working note/generated-note save regressions to prove the extraction preserves their behavior. Reuse those controller tests for the common mechanics and add focused adapter tests for transcript revision handling and source isolation.

Replace the read-only `[data-active-draft]` rendering with an inline editor for structured transcripts. Preserve the existing flat read-only display for flat-only legacy transcripts until a separate general transcript editor is authorized. Keep speaker labels outside the editable text body. Use an unobtrusive contextual whole-turn delete action and an add-unattributed-block affordance; do not add persistent per-turn Save/Cancel or Delete toolbar controls. Render recording/session headings and `?` for null speaker attribution. Explain edit timing and edited status. Preserve PII highlighting using explicit canonical-offset mapping, not global HTML replacement. Keep transcript word/block counts based on canonical text unless product UX explicitly chooses a labeled count. Do not make the masked PII view editable; require the existing explicit reveal flow first.

Implement owner-authorized structured update endpoints with strict size/count/time/order validation, CSRF as required for browser routes, revision conflict checks, and no content in error diagnostics. Ensure API response models return only owner-authorized turn content. Update route audit manifest for any `/api/v1` changes and run its documented authorization audit.

Proposed request contract: an owner-only structured-source read returns its revision token and ordered blocks; update/delete operations identify a turn and expected revision, while insert identifies an adjacent block and expected revision. An update accepts text only, never replacement speaker, timing, scope, or ownership fields. The server derives order, new unattributed identity, timestamps, and the next immutable revision. Return a controlled conflict for a stale token, and test a lost save-response followed by retry so accepted edits are not duplicated. Keep these schemas separate from provider structured-output schemas.

For mixed consultations, preserve earlier flat text as unattributed legacy blocks when the first structured recording is added. Subsequent non-diarised consultation audio appends unattributed blocks through the same source writer; it must not flatten or erase existing turns. Freeze the effective setting separately for every new recording/upload. Turning the preference off does not remove existing labels or the saved-source generation guidance.

### 4. Eligibility controls and bounded diarisation settings

Add admin availability per team STT configuration and connection type (live/batch), scoped to the team’s existing provider configuration authority. Do not grant transcript content access. Add a user preference defaulting off, independent of currently selected provider, and preserve it across STT selection changes. At capture start snapshot effective preference and eligibility into the existing ingestion/session execution snapshot; dictation paths must force disabled. Deepgram live and supported batch paths are eligible only when admin-enabled. Custom live chunk upload is always unavailable in v1. For unavailable selections, return server-derived capability and show a toast while retaining the preference. Add once-per-user recording boundary warning state using an appropriate user preference/acknowledgement mechanism; do not store it in browser storage. Warn once per upload for missing labels. Toasts must be edge-triggered by a real selection/capability change or a completed upload result, never repeated during polling.

Inspect existing config revision/snapshot semantics before deciding where availability is stored: adding fields to a provider config revision may be appropriate, but do not mutate established config history or selection snapshots without matching migrations/tests. Ensure changes affect new captures only; active sessions use their frozen settings.

### 5. Documentation, UI verification, and rollout

When implemented, update maintained current docs identified in `docs/README.md`: `docs/transcript-capture.md` for storage/version/lifecycle and editing semantics, `docs/live_stt.md` for scopes across continuous connection and exceptional reconnect, `docs/stt-config.md` for admin/user availability and eligibility, `docs/workspace.md` for editor behavior, and `docs/testing.md` if verification procedure changes. Add a migration and migration tests as needed. Run maintained-document validation.

## Required validation

- Persistence/service tests: owner-key encryption/decryption for turn text and snapshots; same-owner access only; root deletion/expiry behavior; transaction rollback consistency; version monotonicity; invalid order/time/scope rejection; stale-revision conflicts; no unencrypted clinical content in metadata.
- Ingestion tests: Deepgram live turn assembly across interim/final messages and ordinary checkpoints; one scope across normal socket reuse; new scope after exceptional reconnect; batch mappings; configured custom batch mapping; custom live rejection; missing labels preserve text as unattributed; deterministic ordering; duplicate delivery idempotency; no duplicate turn on retry; quota/checkpoint behavior unchanged.
- Redaction tests using synthetic inputs: speaker labels such as `Speaker 1` and `?`, common clinician/patient lines, names and identifiers inside turn text, multiple sessions, edited text, and offset mapping. First record observed detector behavior. Only propose adaptation if evidence demonstrates false positives or incorrect offsets. Verify canonical text contains no rendered label/headings and redacted-copy output follows established contract.
- Generation tests: immutable structured snapshot used after edits; speaker/session labels rendered for model input only through the established redacted boundary; role caution instruction appears only for diarised saved source; no forced role when uncertain; dictation and Working note stay distinct; generation output schema/validation stays unchanged; regeneration uses frozen source snapshot.
- API/security tests: owner-only retrieval/edit/delete; cross-owner IDs rejected; metadata/admin users cannot read content; expired roots unavailable; strict request schema/size bounds; route audit manifest updated; API authorization audit.
- Browser tests: inline per-turn edit isolation, paste/newline behavior, contextual explicit whole-turn deletion (empty text does not delete), add unattributed turn, labels/heading rendering, PII offset mapping, accessible keyboard focus, 700 ms autosave debounce, serialized requests and queued edits during inflight save, stale response cannot clear newer dirty edits, server conflict handling, failed-save retry with memory-only draft, poll does not replace dirty editor, flush before generation/workspace navigation/new recording, capture-state read-only behavior, toast once semantics, and preference persistence across provider changes.
- Run focused tests first using the project virtual environment and required test env vars; follow `docs/testing.md` and `docs/dbtesting.md`. Run pytest and API audit sequentially due shared test infrastructure. Do not claim real-provider verification unless it is actually run; synthetic fixtures should be the default.

## Implementation decisions

- Current turns and immutable version snapshots use established owner encryption; the latest matching version identifies the editable revision.
- Legacy flat-only consultations remain read-only.
- Recording headings separate uploads and actual provider reconnects. Speaker presentation numbers persist through turn deletion.
- Conditional generation guidance treats attribution as uncertain, infers roles from context, and does not assume exactly two speakers. The generated-output schema remains unchanged.

## Architectural guardrails

The user has authorized the structured storage, versioning, provider controls, and editor changes described here. Keep transcript-derived content owned by the transcript owner and encrypted with established user-content services. Preserve retention/deletion at the transcript root, source snapshot immutability, redaction fail-closed behavior, provider attempt/quota semantics, and generated-draft review. Do not pass content into team/admin views or logs. Escalate any solution that requires changing one of those invariants.
