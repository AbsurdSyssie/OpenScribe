# Consultation problem plans and split-note generation

Status: current behavior. A consultation has a mutable, owner-encrypted problem plan that can be edited independently of submitted note batches. Automatic detection is optional; a saved manual plan takes control for that consultation. Submitted batches freeze source, plan, template, provider, and lineage snapshots and remain unchanged by later edits. Split-note generation remains draft-only and requires clinician review.

## Living problem plan

**Review problems** is available to the owning clinician when the deployment and owner capability are enabled, including for a transcript with no prior analysis. Opening Review does not save sources or start provider work. The Primary note tile always exists. A clinician may add problem titles and note tiles, choose one Primary tile, assign problems to tiles, and select one template per tile. A Primary-only plan can create one note, even with no named problem. A secondary tile needs at least one assigned problem.

Drag a problem by its grip to another note; the **Move to…** menu provides a keyboard- and touch-friendly alternative. If fewer than six notes exist, moving at least 24px outside all note tiles and dwelling in the bounded board gutter or Add note area for about 200ms expands the compact **Add note** button across its existing row as **Drop here to create a note**. Dropping directly on **Add note** is also explicit intent after 24px of movement without the dwell. This target does not change the grid or modal size; reentering a tile, cancelling, pressing Escape, or dropping elsewhere clears it without changing the plan. An unrelated workspace refresh with the same or omitted plan preserves the native drag; a transcript-root, capability, lock, or plan change cancels it. A successful drop creates a note with the Primary template and moves the problem into it. Making a note Primary moves it to the front with a short slide animation, which is suppressed when reduced motion is requested.

Every tile is labeled **Note 1**, **Note 2**, and so on, with a full-width header: teal-tinted for Primary and warm neutral for secondary notes. A **Primary** or **Make primary** chip sits beside the note number; selecting it promotes the same tile while preserving its identity and problem assignments. Each outlined problem box has a grip, bold inline title, **Ignore** (EyeOff), and **Delete** (Trash2) on its first row, with a full-width **Move to…** selector beneath. A quiet **Add problem** button and compact inline template selector sit at the tile bottom. The Primary tile cannot be deleted.

The plan autosaves quietly. Routine save, suggestion-ready, and note-queued confirmations do not appear in Review; the plan, loading animation, and generated-note state show progress. Actionable errors, conflicts, and blocked-state guidance remain visible. The first manual change makes the plan manual for this consultation and suppresses automatic suggestions; the clinician can still explicitly request **Auto suggest** later. Suggestion generation replaces the modal controls with its in-modal progress animation. On success it replaces the suggested grouping while preserving ignored problems; on failure the existing plan remains available. A reset warning explains that successful suggestions replace current groupings. While suggestion generation is active, plan controls are unavailable.

**Ignore** excludes a problem's source content from every generated note. It is unavailable until the problem has a nonblank title. **Delete** removes only its explicit routing assignment; its source content remains available to the Primary note. Ignored problems remain restorable from the **Ignored** list. Restoring returns a problem to its former tile if that tile remains, otherwise to Primary. Removing a secondary tile returns its assigned problems to Primary. The Primary tile cannot be deleted; another tile must first become Primary. These actions affect the live plan only and never rewrite source content or an already submitted batch.

The Primary note includes its assigned problems and otherwise unassigned source material, excluding problems routed to secondary notes and all ignored problems. Secondary notes contain only source material relevant to their assigned problem titles. Titles are routing labels, not facts; the generator must not invent content for an empty scope. Every output tile has one template. Moving problems between tiles changes their routing, not the destination template.

Manual changes persist across transcript, Working note, and dictation edits. **Create** uses the latest successfully saved and redacted consultation sources with the current saved plan. It waits for autosave and source preparation. New suggestions or edits never cancel a submitted batch. **Retry missing notes** retries only the original failed outputs using that batch's frozen source, grouping, templates, and exclusions; a later **Create** uses the current plan and makes a new batch.

The plan has at most six named problems, including ignored problems, and at most six output-note tiles. The modal widens with the number of tiles (approximately 28rem for one, 52rem for two, 72rem for three, and up to 110rem for four or more, capped at 94vw), uses a 20rem minimum tile width, wraps as needed, and stacks tiles on narrow screens. The server keeps the problem plan under the transcript owner's encryption and retention boundary. Manual problem titles cross the existing redaction boundary before provider submission; raw titles and the PHI mapping are not included in provider requests. Only the transcript owner can read or change plan content; team roles do not grant access.

## Availability and automatic suggestions

`CONSULTATION_SPLITTING_ENABLED` and the owner's eligibility determine whether problem review and split-note creation are available. The owner preference `split_consultations_into_separate_notes` controls automatic suggestion on an untouched consultation; saving a manual plan overrides automatic suggestions for that consultation. Manual control does not disable the explicit **Auto suggest** action. Availability is not a content-sharing permission: only the transcript owner may access the plan, source snapshots, and generated notes.

Review can open for a saved transcript even when no analysis exists. Opening it does not save source text or call a provider. **Auto suggest** prepares current saved sources, then submits a durable owner-scoped suggestion intent. The modal replaces its controls with a progress animation until the operation finishes. On success, suggested problems and groupings replace the live plan while ignored problems remain excluded; on failure, the saved plan remains usable. Repeating an idempotency key replays the same operation. Manual edits do not cancel a suggestion already submitted, and a suggestion result is applied only to the plan revision it was based on.

### Compatibility path for untouched automatic consultations

An untouched consultation with automatic splitting enabled may still use the existing analysis-and-intent flow: **Create** queues or reuses source-bound analysis, and a multi-problem result opens clinician review. An accepted legacy intent continues under its frozen owner, source, and retention binding even if the preference later changes. Existing draft routes remain available for that compatibility flow. A saved manual plan uses the direct plan-based Create path described below; it does not require an analysis draft. Existing version-1 submitted batches retain their exact legacy generation request reconstruction.

## Plan persistence and API

`GET` and `PUT /api/v1/transcripts/{transcript_id}/consultation-problem-plan` read and replace the living plan. The replacement requires `expected_revision` and an `operation_id`; concurrent edits fail with a revision conflict instead of silently overwriting one another. The plan is encrypted under the owning user's content key and follows transcript-root retention/deletion. Workspace REST/SSE exposes only the current owner's plan projection.

`POST /api/v1/transcripts/{transcript_id}/consultation-problem-suggestions` starts explicit Auto suggest. It requires an idempotency key, expected revision, and an accessible selected template; a failed analysis can only be retried explicitly. `POST /api/v1/transcripts/{transcript_id}/consultation-note-batches` creates a batch from the saved current plan and latest successfully prepared redacted source. Both are owner-only, CSRF/origin protected, no-store operations subject to the existing generation transport limits. The suggestion response exposes safe operation state; the create response exposes only batch ID, queued status, counts, timestamps, and replay state.

The confirmed plan is an encrypted versioned snapshot. Version 2 records the problem-plan ID and revision, one output UUID per note tile, order, exactly one Primary tile, the tile template snapshot, redacted problem scopes, and ignored titles. A Primary-only plan is valid and yields one note. There is one durable batch topic and one outcome per output tile; ignored problems do not become extra note topics. Existing accepted version-1 batches retain their legacy request reconstruction.

## Create, immutability and recovery

Create waits for a successful plan autosave and the latest saved source/redaction preparation. If preparation or saving fails, no batch is accepted. The transaction freezes the exact plan, source and PII mappings, templates, provider execution snapshot, and transcript lineage before queuing work. Editing or requesting suggestions while a batch is in flight changes only the live plan. The submitted batch proceeds or fails using its original frozen inputs and is never canceled by later UI edits.

Provider-bound source content and routing titles are redacted. The provider receives only validated redacted source values, clinical hints, and redacted problem titles. It never receives the PHI mapping or source lineage metadata. Placeholder validation checks generated output before encrypted persistence; placeholder restoration occurs only at owner-only materialization. Every generated note is a clinician-review draft.

After a batch reaches a terminal state, **Retry missing notes** uses the original batch's failed tile IDs and immutable source/plan/template snapshots. A new Create uses the current live plan and creates a new batch. **Keep available notes** materializes validated survivors without provider work. Workspace status contains safe lifecycle information and opaque IDs, not titles or note contents.

The optional hallucination checker receives only validated redacted source fields, bounded clinical hints, the redacted confirmed plan, and validated structured survivors. It does not receive the source PHI mapping or lineage metadata. It may return only the existing exact-substring structured-section edits; corrections are stored separately from accepted output. If the optional check fails, originals remain usable clinician-review drafts. A previously queued checker request built from the broader legacy source snapshot fails canonical request matching before another provider call and is finalized unchecked; accepted outputs remain unchanged.

## Partial recovery

Initial and recovery generation queues reserve tokens from the exact adapter-specific request using the established UTF-8 input estimator and the submitted output cap. Gemini retains its 30,000-token ceiling; other adapters retain the nominal per-note cap. Bundled verification uses the same reservation rule with its independent checker request. The larger accurate reservation can reject generation before submission or leave optional verification unchecked when quota is insufficient. Settlement still uses reported usage or the established unknown-outcome policy.

A durably persisted provider response, including a malformed durable response, may retain valid topic outcomes encrypted, mark only failed requested topics, and queue one automatic retry using the initial execution's frozen provider configuration and model. New recovery provider schemas allow only the failed-topic UUID set; retained validated siblings remain immutable context. Already-queued legacy requests retain their broader schema only when the complete request exactly matches its legacy reconstruction from immutable batch snapshots. The response parser always enforces the failed-topic set. A submitted attempt with no durable response, including a timeout or uncertain transport failure, never enters automatic recovery.

**Retry missing notes** is an explicit clinician action. It uses the current eligible provider selection, creates a fresh execution, quota reservation, and outbox row, and includes retained siblings only as immutable encrypted context. The batch lock lets a simultaneous automatic and manual retry create at most one second execution.

**Keep available notes** is an owner-only database action. It materializes each validated survivor once, replays the same children on a later request, and is rejected while a recovery execution is active. It never invokes a provider or consumes LLM quota. Workspace REST/SSE sends only safe status, counts, action flags, and IDs. It sends no topic output, provider, quota, or recovery detail. If the primary failed, the browser gives an accessible warning before Keep; after `completed_partial`, it states that a surviving secondary note was selected. Split children remain clinician-review drafts.

## Optional bundled verification

Before full materialization, and before **Keep available notes** for a partial survivor set, the service can use the independently configured team hallucination checker. A trusted partial initial response first reaches a terminal automatic-recovery decision. If recovery runs, verification waits for that recovery to complete or fail definitively; it then snapshots the stable complete set or stable survivors. The service never queues verification while a recovery is active. It queues one verification execution with its own reservation and outbox task. Credentials resolve outside the final transaction; the attempt commits as submitted before the one provider call. Duplicate delivery never makes a second call, and a recoverable encrypted response allows local finalization only.

Only an all-structured survivor set is eligible. The checker receives the immutable encrypted batch source, plan, clinical NLP snapshot, and exact survivor UUID set. It may return only the existing exact-substring structured-section edits. The service applies the complete valid envelope in memory and revalidates every corrected output before storing it in `verified_output_encrypted`; it never changes accepted output. Mixed/freeform sets have no patch protocol and are durably `unchecked`.

Gemini requests include that generated patch schema. The split request secret-name scan recognizes only the canonical `section_key: {"type": "string"}` schema property as non-secret metadata; it still rejects credential keys in request configuration, other schema properties or altered definitions. Runtime output validation remains unchanged. Consumed finalization errors emit `consultation_split_finalization_failed` with an execution UUID and fixed phase, without exception details or content.

No selected/valid checker, unavailable credentials or quota, expiry, provider error or timeout, malformed response, or failed patch is fail-open. The batch records only bounded safe verification metadata and original validated outputs still materialize as clinician-review drafts. Workspace REST/SSE and browser status show only lifecycle state and correction count. They do not expose source material, verifier response, edits, provider metadata, or reasoning. Keep and retry controls stay unavailable while the batch is verifying.
