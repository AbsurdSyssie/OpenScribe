# Split note user experience

## Design discussion: intended behaviour

This records accepted UX direction for consultation problem planning. It is design discussion, not an implemented contract.

- **Problem title** is the short name identifying a problem for a split note. Avoid **Description** as an alias; no separate clinical description is implied.
- Review is available for a transcript-only consultation before any split analysis. The user can start a manual plan by adding a primary problem; Auto suggest is optional.
- The first saved manual plan change, whether creating the initial plan or changing an AI-suggested plan, switches that consultation to manual control. Changes include renaming a problem, changing its template assignment, moving it between tiles, changing a tile's primary status, ignoring or deleting a problem, and adding a problem. This does not change the user's global preference.
- For an untouched consultation with automatic splitting enabled by preference, **Create** runs AI suggestions. If the result proposes multiple output notes, open Review and wait for clinician confirmation; if it produces one note, generate it directly without opening the modal. A saved manual plan takes precedence and turns off automatic analysis for that consultation.
- The review should show note tiles, with problems assigned to output-note containers. A problem can move between any containers, and multiple problems can be grouped in one output note. For example, **Knee pain** and **Blood pressure** may share one note, while **Sleep concerns** and **Medication review** share another.
- Drag a problem by its grip to move it between notes. If fewer than six notes exist, moving at least 24px outside all note tiles and dwelling in the bounded board gutter or Add note area for about 200ms expands the compact **Add note** button across its existing row as **Drop here to create a note**. Dropping directly on **Add note** is also explicit intent after at least 24px of movement and does not require the dwell. The target changes no grid or modal dimensions; reentering a tile, canceling, pressing Escape, or dropping elsewhere clears the target without changing the plan. An unrelated workspace refresh with the same or omitted plan preserves the native drag; a root, capability, lock, or plan change cancels it. A successful drop creates a secondary note using the Primary template and moves that problem into it. The per-problem **Move to…** menu remains the keyboard- and touch-friendly alternative.
- Manual problem-to-note groupings and tile templates persist when the transcript, Working note, or saved dictation changes. A source change does not force **Auto suggest** or discard the grouping.
- The plan autosaves quietly instead of using an explicit **Save plan** button. Omit routine saved, suggestion-ready, starting, and queued confirmations in Review; rely on the visible plan, loading animation, and generated-note state. Keep actionable errors, conflicts, and blocked-state guidance. Save title edits after a short pause; save problem moves, deletions, and template changes immediately. **Create** waits for a successful save and stays blocked while changes are unsaved or a save has failed. Preserve local edits when a save fails.
- **Primary** belongs to the whole output-note tile, not an individual problem. The Primary tile always exists, including when there are zero named problems. Moving a problem between tiles does not carry the primary designation with it. The primary note is the catch-all for source content not related to problems assigned to secondary notes, except content for explicitly ignored problems. Secondary notes cover their assigned problem groups.
- Visually label each tile **Note 1**, **Note 2**, and so on, with full-width headers: teal-tinted for Primary and warm neutral for secondary notes. Place the **Primary** or **Make primary** chip beside the note number; promotion preserves the tile UUID and assignments. Give each outlined problem box a first row with grip, bold inline title, **Ignore** (EyeOff), and **Delete** (Trash2), followed by a full-width **Move to…** selector. Place a quiet solid **Add problem** button and compact inline template row at the tile bottom. Never offer deletion of Primary. Keep **Add note** compact at rest; reserve dashed borders for active drag targets.
- Deleting a secondary note tile moves all its assigned problems into the existing Primary tile, then removes the secondary tile and its template choice. No content is ignored and there is no unassigned problem pool. Primary has no **Delete note** action; first make another tile Primary to remove the current Primary tile.
- **Add note** creates a temporary secondary tile with one blank problem row and focuses its title. Initially copy the current Primary template into the new tile; the user can edit it. A blank incomplete tile is not generated or saved as a valid note. If it is still empty when Review closes, discard it.
- If moving or deleting a problem leaves a secondary tile empty, remove that tile automatically. Keep the Primary tile when it has no named problems.
- Do not automatically open Review for a primary-only plan. If Review is already open, it may remain open when edits leave only the Primary tile.
- Each output-note tile has one template, used by every problem in that note. Moving a problem to another tile makes it use the destination tile's template and does not change that template.
- **B** is the chosen responsive layout. The common case is 2–3 problems; 4 or more is uncommon. On desktop, widen the modal according to the number of output-note tiles, not the number of problems: approximately 28rem for one tile, 52rem for two, 72rem for three, and up to 110rem for four or more, capped at 94vw. Keep a 20rem minimum tile width and wrap when needed; stack tiles on narrow screens.
- The user can still explicitly choose **Auto suggest** in Review; this prepares or replaces the plan only and never generates notes. After a reset warning, preserve the current note grouping while the request runs and replace it only when a valid result succeeds. On failure, restore the existing plan controls with an error and **Retry** option. Auto suggest may replace note grouping, but ignored-problem exclusions persist; any ignored problem remains excluded until explicitly restored. The reset warning must say that the grouping will be replaced on success and ignored problems will remain excluded; it does not reset exclusions.
- While **Auto suggest** is running, replace the modal's problem controls with a generation animation/loading view; problem editing is unavailable until the suggestion request finishes. This lock applies only to suggestion generation.
- In manual mode, **Create** inside Review uses the current visible, saved problem-to-note grouping and the latest successfully saved consultation sources without running automatic analysis again. Create an ordinary one-note draft from Primary when saved source content exists, even if there are zero named problems. Secondary output-note tiles produce notes for their assigned problem groups.
- While a note batch is in flight, Review, editing, autosave, and explicit **Auto suggest** remain available. Suggestion generation locks the problem controls only while that suggestion request is running. Keep **Create** disabled until the current batch finishes to avoid overlapping submissions and output slots. Editing or suggesting does not cancel or alter the batch already submitted; it keeps its original sources and plan.
- Automatic provider retries replay the immutable submitted request, not later edits. **Retry missing notes** stays beside failed outputs outside the live plan modal and retries the original failed batch with its original sources, grouping, templates, and exclusions. Its wording explains that it retries the original plan, even if the live plan has since changed. **Create** inside Review uses the current visible saved plan; it does not silently retry an older batch.

## Problem actions and terminology

- Use **Ignore** for **“ignore this problem.”** Ignore excludes the problem from all generated notes.
- **Delete** removes the problem's explicit planning/routing assignment. Its source content remains unchanged and returns to Primary. Delete is not a clinical exclusion.
- Ignored problems remain visible and discoverable from the modal. Use a compact **Ignored (count)** button in the footer beside **Auto suggest**; it opens a small popover over the content without shifting note tiles or resizing the modal, and closes on outside click or Escape. The popover lists ignored titles with **Restore** actions. The full-width strip was rejected as too space-consuming.
- **Restore** returns the problem to its previous note tile if that tile still exists; otherwise, it returns to Primary. Restore does not recreate a deleted tile. The clinician can move the problem afterward.
- Transcript, Working note, and saved dictation source content remains untouched by either action. Already submitted notes keep their original sources and plan.
- The implementation must explain the difference between Ignore and Delete in the controls and user-facing Help.

## Proposed detail

The responsive widths above reflect the current layout implementation. The user has exercised the flows and reported that they work well; automated regression coverage follows that review.

## Implementation status — 2026-11-04

The living owner-encrypted problem plan, autosaving tile/problem editor, explicit Auto suggest flow, and grouped version-2 frozen batch contract are implemented. Submitted batches keep their source, plan, template, provider, and transcript-lineage snapshots; the live plan remains editable independently. The new manual Create path supports a Primary-only plan with no named problems.

The user completed an initial manual flow review and authorized regression tests on 2026-11-04. Automated coverage exercises living-plan persistence, owner boundaries, source retention, suggestions, grouped batch snapshots, editor actions, drag behavior, and responsive layout. Test execution results and any remaining limitations are reported with the implementation; this record does not imply exhaustive end-to-end verification. Discovered issues are recorded in [DISCOVERED_ISSUES.md](../DISCOVERED_ISSUES.md).

Current behavior and API contracts are documented in [consultation-splitting-preference.md](../docs/consultation-splitting-preference.md) and [api.md](../docs/api.md). This plan remains the accepted intended UX and implementation record; if its design details and runtime differ, those maintained documents describe current behavior.
